# 模拟业务数据设计

## 一、数据边界

本项目只使用合成数据。所有名称、编号、金额、联系人和业务关系均由脚本生成，与任何真实公司、客户和个人无关。

数据生成必须满足：

- 固定随机种子，可重复生成。
- 业务关系和金额逻辑可解释。
- 预设异常可稳定复现。
- 不包含真实手机号、邮箱、身份证、合同号或公司名称。
- README 明确标注数据为 synthetic/demo data。

## 二、第一版数据库

数据库名称：`enterprise_demo`

### 组织与客户

| 表 | 作用 | 关键字段 |
|---|---|---|
| `org_department` | 部门与区域 | `id`、`name`、`region`、`parent_id` |
| `employee` | 销售及负责人 | `id`、`department_id`、`name`、`email` |
| `customer` | 客户主数据 | `id`、`name`、`industry`、`region`、`credit_level` |
| `contract` | 合同 | `id`、`customer_id`、`contract_amount`、`start_date`、`end_date`、`status` |

### 销售与应收

| 表 | 作用 | 关键字段 |
|---|---|---|
| `sales_order` | 销售订单主表 | `id`、`order_no`、`customer_id`、`department_id`、`order_date`、`total_amount`、`status` |
| `sales_order_item` | 订单明细 | `id`、`order_id`、`product_name`、`quantity`、`unit_price`、`amount` |
| `receivable` | 应收单 | `id`、`order_id`、`due_date`、`receivable_amount`、`received_amount`、`status` |
| `payment` | 回款记录 | `id`、`receivable_id`、`payment_date`、`amount`、`channel` |

### 预算、费用和 KPI

| 表 | 作用 | 关键字段 |
|---|---|---|
| `budget` | 部门月度预算 | `id`、`department_id`、`period`、`category`、`budget_amount` |
| `expense` | 实际费用 | `id`、`department_id`、`expense_date`、`category`、`amount`、`status` |
| `kpi_definition` | 指标定义 | `id`、`code`、`name`、`formula_description`、`unit` |
| `kpi_target` | 指标目标 | `id`、`kpi_id`、`department_id`、`period`、`target_value` |
| `kpi_value` | 指标实际值 | `id`、`kpi_id`、`department_id`、`period`、`actual_value` |

## 三、核心关系

```text
org_department 1 -> N employee
org_department 1 -> N sales_order
customer 1 -> N contract
customer 1 -> N sales_order
sales_order 1 -> N sales_order_item
sales_order 1 -> 0..1 receivable
receivable 1 -> N payment
org_department 1 -> N budget
org_department 1 -> N expense
kpi_definition 1 -> N kpi_target
kpi_definition 1 -> N kpi_value
```

金额字段统一使用 `DECIMAL(18, 2)`，日期和统计周期使用明确的时区与格式。订单号、合同号使用项目自己的前缀，不模拟真实企业编码。

## 四、建议数据规模

- 8 个部门，覆盖 4 个区域。
- 80 名员工。
- 500 个客户。
- 800 份合同。
- 24 个月数据。
- 20,000 笔销售订单。
- 50,000 条订单明细。
- 约 18,000 条应收单。
- 20,000 到 30,000 条回款记录。
- 每部门每月 4 类预算与费用。
- 10 个 KPI 指标及对应目标和实际值。

第一版优先保证数据质量，不为制造“大数据量”盲目增加记录。

## 五、生成规则

### 正常业务规则

- 只有 `APPROVED` 订单计入销售额。
- 订单金额等于明细金额合计。
- 应收金额原则上等于审核订单金额。
- 回款累计金额不能超过应收金额。
- 回款完成后应收状态变为 `PAID`。
- 预算执行率等于已审核费用除以预算金额。
- KPI 完成率等于实际值除以目标值。

### 预设异常

| 异常编号 | 场景 | 注入规则 | 期望问题 |
|---|---|---|---|
| A01 | 销售下降 | 华东一部最近 3 个月订单金额逐月下降 | 哪个部门销售额连续下降？ |
| A02 | 预算超支 | 市场费用为预算的 125% | 哪个部门本月费用超预算？ |
| A03 | 应收缺失 | 5% 已审核订单不生成应收单 | 哪些订单没有生成应收？ |
| A04 | 逾期未回款 | 部分应收到期 60 天后仍未结清 | 哪些客户存在长期逾期？ |
| A05 | KPI 未达标 | 两个部门连续两个季度低于目标 | 哪些 KPI 连续未达标？ |
| A06 | 金额不一致 | 少量应收金额与订单金额不一致 | 哪些订单和应收金额不一致？ |

异常比例写入配置，不散落为脚本中的魔法数字。

## 六、指标口径

| 指标 | 口径 |
|---|---|
| 销售额 | 已审核订单的 `total_amount` 合计 |
| 回款金额 | 指定期间 `payment.amount` 合计 |
| 应收余额 | `receivable_amount - received_amount` |
| 回款率 | 回款金额 / 应收金额 |
| 预算执行率 | 已审核费用 / 预算金额 |
| KPI 完成率 | 实际值 / 目标值 |
| 逾期天数 | 查询日期 - 应收到期日 |

所有指标都要准备：中文名称、英文或字段映射、公式、时间口径、组织口径、排除条件和一个标准 SQL 示例。

## 八、数据验收

M1 完成前至少验证：

- 所有外键关系有效。
- 订单金额等于正常明细合计。
- 正常回款不超过应收金额。
- 每类预设异常数量与配置一致。
- 同一固定种子重复运行得到相同记录和统计结果。
- 重新初始化不会产生重复主键或重复业务编号。
- 验证 SQL 能准确定位 A01 到 A06。
